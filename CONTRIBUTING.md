# Contributing to AvLoader

Thank you for your interest in contributing to AvLoader!
This library aims to provide a clean, stable, and importer-agnostic core API for loading avatars in Unity,
while still allowing advanced access to importer- and plugin-specific functionality when appropriate.

These are shared expectations, not rigid laws.
If you believe a guideline should be intentionally violated for good reason, explain why — preferably both
in the PR description and with a comment in the code.

## General Principles

- Favor clarity over cleverness.
- Prefer explicit APIs over implicit behavior.
- Avoid leaking importer-, plugin-, or format-specific concepts into the *core* public API.
- Changes to public APIs should be additive when possible.

## LoadedAv, Loaders, and Importers

`LoadedAv` represents a loaded avatar instance and is the **sole owner** of all runtime objects associated
with that avatar.

Loaders and importers are responsible for **generating** runtime objects, but they do not own them.
All ownership, lifetime management, and disposal responsibility belongs to the `LoadedAv` implementation.

## LoadedAv and Importer Responsibilities

Importer-backed `LoadedAv` implementations MAY:

- Expose **library- or plugin-specific avatar instance objects** that were generated during import.
- Manage the lifetime of those objects internally via `ImporterSpecificDispose()`.

Examples of allowed exposed instance objects:
- UniVRM: `Vrm10Instance`, `RuntimeGltfInstance`
- glTFast: `GltfImport`
- UniGLTF: `RuntimeGltfInstance`

These instance objects:

- Exist *because* a specific importer/runtime library was used
- Are generated as part of the import process
- Are owned, disposed, and lifetime-managed exclusively by the `LoadedAv` instance
- Are intended for advanced users who understand the underlying plugin

Exposing such objects is **explicitly allowed** in `LoadedAv` implementations.

## Capabilities

The `Uralstech.AvLoader.Capabilities` namespace is reserved for
**importer- or runtime-library-defined capabilities**.

Capabilities represent *functionality that exists because a specific importer or plugin generated it*,
independent of how or whether it is later configured.

Rules:

- Capability interfaces must represent functionality defined by a specific importer, format, or runtime library.
- Capability interfaces must only be implemented by importer-backed `LoadedAv` implementations.
- Post-processors and user code must not implement capability interfaces.
- Capabilities expose **availability and guarantees**, not configuration, policy, or ownership.

Examples:
- ✔ VRM LookAt
- ✔ VRM Expressions
- ✔ Importer-generated Animator (e.g. UniVRM)
- ✖ Animators added by post-processors or user code
- ✖ Generic Unity components that can exist independently of the importer

## Post-Processors

Post-processors may:

- Configure or modify importer-generated systems (e.g. animator controllers, look-at targets).
- Add new Unity components or runtime objects.
- Register owned objects using `RegisterLifetimeObject`.

Post-processors must **not**:

- Implement capability interfaces.
- Redefine or replace importer-generated runtime systems in a way that breaks capability guarantees.

## Public API Guidelines

### XML Documentation

- All public types, methods, properties, and fields must have XML documentation.
- Documentation should describe intent, guarantees, and lifetime expectations.
- Use `<remarks>` to clarify ownership, disposal behavior, or edge cases when relevant.

This ensures the API remains understandable via IntelliSense without requiring external documentation.

### Code Style and EditorConfig

This project uses `.editorconfig` to enforce consistent code style.

- EditorConfig rules should be followed by default.
- Deviations are acceptable when they improve clarity or correctness.
- When deviating, include a brief justification comment.

Example:
```csharp
[SuppressMessage("Style", "IDE0046", Justification = "Avoids double conditional, improves readability.")]
```

## Lifetime and Ownership

* `LoadedAv` owns the lifetime of all runtime objects associated with an avatar.
* Objects generated by loaders, importers, or post-processors must be registered using `RegisterLifetimeObject`
  unless ownership is explicitly transferred.
* Ownership transfers (e.g. via deregistration) must be clearly documented in code.

## Pull Requests

* Keep pull requests focused and reasonably sized.
* Avoid mixing refactors with functional changes.
* If a change affects public APIs or observable behavior, explain the rationale in the PR description.

Thank you for helping keep AvLoader clean, consistent, and maintainable.
